01The model: one ladder of intent

The four layers are not four separate features. They are one ladder, each level answering a different question and defined by the level below it. You reach for only the depth the work needs.

LayerAnswersLinear objectCompletes?
Projectwhy — the outcomeProject (≈ product, 1:1 for now)eventually
Milestonewhat deliverable, by whenProjectMilestoneyes — a checkpoint
Taskthe goal — what "done" meansIssueyes — proven by proof
stepshow — the pathnone (checklist / local todo)disposable
the reframe A milestone is the deliverable — its description is the "done when…", its issues are the work that produces it. No separate deliverables object. And steps are not sub-issues: they're disposable scratch. A sub-issue is only for a step big enough to be independently delegated.

Where cycles fit — the time axis, crossing the ladder

Cycles are not a level in the ladder. The ladder is the scope axis (what the work is, what it belongs to); a cycle is the time axis (when you schedule it). Every task has both coordinates, and they cross: one milestone's tasks spread across several cycles, and one cycle pulls tasks from several milestones.

the crossing to build --project / --milestone widen to all cycles by default (you want the whole deliverable, not this week's slice) — unless you also pass --cycle. Two cross-axis views: tasks --cycle active --by-milestone (what this sprint delivers) and tasks --milestone v1.0 annotated by cycle (is it on track for its date).

02A goal is the open half of the proof contract you already have

A to-do list is a plan of steps — brittle; an agent optimizing "check off steps" drifts from the outcome. A goal is the success condition — durable; a smart agent holds it fixed and regenerates the steps. The CLI is already proof-first at close, but nothing captures the target at open, so the proof is unanchored. The goal is simply what the proof is meant to satisfy.

When is a goal needed? When the title is already a crisp acceptance criterion (Bump version to 0.14.0) the title is the goal — no extra field. When the task is fuzzy (Improve project management) the goal is what converts it into executable work. Rule of thumb: an agent should not start a fuzzy task before writing its goal.

Goal seeding — the one snippet worth previewing

# linear create "Fix auth refresh" --goal "tokens refresh on expiry; e2e login passes"
# writes into the issue description:
## Done when
- tokens refresh on expiry
- e2e login passes

# at close, the CLI prints the goal next to the proof so close is a checked contract:
linear update ANT-42 --done --proof https://pr/123
  goal:  tokens refresh on expiry; e2e login passes

05Edges & verification

  • Extra API cost. Rollups need issue-by-milestone counts. Fetch counts in the existing project/milestone query where possible; fall back to one issues(filter:{projectMilestone}) aggregate per project — measured, not per-issue.
  • Orphan bucket is the feature, not a warning. Issues with no milestone group under an explicit "No milestone (N)" heading — that surface is literally "what isn't matched".
  • Goal lives in the description. A ## Done when block is parsed/round-tripped so --goal edits don't clobber the rest of the description body.
  • Backward compatible. Every new flag is additive; existing commands unchanged. Tests go in test_linear.py (1:1 with the script) + a real --json round-trip against the API.
  • Proof of done. Run each new command against the live workspace, capture output, attach to the PR.
